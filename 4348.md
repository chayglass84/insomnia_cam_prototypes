**The OAuth flow in plain language (for whoever picks this up, or for a refresher):** an OAuth-protected MCP server does not log anyone in itself; a separate *authorization server* (AS) does, and hands out access tokens. The wizard walks the three things a client has to do, one visible step at a time:
1. **Discover.** Call the MCP server with no credentials. A protected server answers `401` and a `WWW-Authenticate: Bearer resource_metadata="..."` header, which points at the *protected resource metadata* (RFC 9728): "these are the authorization servers I trust". Then fetch that AS's *metadata* (RFC 8414, OIDC as fallback): its authorize, token and registration endpoints and what it supports. We check the `issuer` matches exactly and that PKCE S256 is offered (required), and report whether a client can register by CIMD, by DCR, or needs a pre-registered id, and whether the RFC 9207 `iss` check is available.
2. **Register & authorize.** The AS must know *which app* is asking, so the client needs a `client_id`: register itself (DCR, RFC 7591), use a URL that points at a client metadata document (CIMD), or use one an admin registered (this is what "saved clients" remember; refresh tokens belong to one client). Then open the browser at the authorize URL with a PKCE challenge (a hash of a secret kept locally, so a stolen code is useless), a random `state` (CSRF check), the `resource` (RFC 8707, binds the token to this MCP server) and the `scope`. The user signs in and consents in the browser; the AS redirects back to a loopback listener (`127.0.0.1:38491/callback`) with `code`, `state` and `iss`. We reject the response if `state` is wrong or `iss` is not the issuer we started with (a mix-up attack), and we show `access_denied` if the user said no.
3. **Get a token.** Exchange the single-use `code` plus the PKCE verifier at the token endpoint for an access token (and usually a refresh token), then prove it works by calling the MCP server with `Authorization: Bearer`. A `403 insufficient_scope` means the token is valid but too narrow: step-up re-runs step 2 asking for the old scope plus the one the server named. When a token expires, a refresh token gets a new one without the user (we do this before Connect and after a 401, only for tokens the wizard issued).

Every HTTP exchange along the way is its own Call in the Trace, tagged with an OAuth chip; the browser leg is one Call (the authorize URL we opened, and the redirect that came back). The mock authorization server (`mock-authorization-server.mjs`) implements all of it, with an Absolutely / No Way consent page and flags to break each part on purpose.

### S8 enterprise-managed authorization / XAA (built 2026-11-23, uncommitted, not click-tested)

- Spec read for this: the MCP extension "Enterprise-Managed Authorization" (2026-07-28, extension id `io.modelcontextprotocol/enterprise-managed-authorization`) and IETF draft-ietf-oauth-identity-assertion-authz-grant (-04, dated 2026-05-21, whose stated expiry of 2026-11-22 has passed: check for a newer revision before relying on details). Flow: (1) user single-sign-on to the client at the IdP (OIDC, ID token); (2) client trades the ID token at the IdP for an ID-JAG (RFC 8693; `requested_token_type` id-jag, `audience` = the MCP authorization server's issuer, `resource` = the MCP server); the IdP applies admin policy and may refuse; (3) client presents the ID-JAG at the MCP authorization server (RFC 7523 jwt-bearer grant) and gets an access token, no consent page, no refresh token. ID-JAG: header `typ: oauth-id-jag+jwt`; claims iss, sub, aud, client_id, jti, exp, iat (+ resource, scope, email). The client is registered separately at the IdP and at the authorization server.
- **Discover XAA** button next to Discover OAuth (Auth tab) opens a four-step modal: 1 Discover (the OAuth discovery, plus a verdict on whether the authorization server advertises `urn:ietf:params:oauth:grant-profile:id-jag`), 2 Sign in at the identity provider (issuer URL, client id, client secret; IdP metadata lookup, then OIDC code + PKCE in the browser, ID token decoded), 3 Get an ID-JAG (the exchange; the ID-JAG is shown decoded with client-side checks for everything an authorization server rejects it for: typ, iss, aud, client_id, resource, exp, required claims), 4 Get an access token (jwt-bearer with the client's own credentials at the authorization server, then the existing "call the MCP server" proof; the token lands in the Auth tab as Bearer). Every HTTP call is its own OAuth Call in the Trace, so Edit & replay (S5d) works on them: edit the ID-JAG or the jwt-bearer request and see how the server reacts. A flawed ID-JAG is deliberately still kept and sendable, so a developer can see the authorization server's reaction. An ID-JAG is single use; "Exchange again" gets a fresh one from the IdP (the ID token is reused until it expires).
- **Discoverability:** when Connect fails with an OAuth challenge, a background check (`discoverOAuth`) sets `state.xaaSupported`; if the authorization server accepts ID-JAGs the existing "This server asked for OAuth" banner says so and offers **Discover XAA** next to Discover OAuth. The OAuth wizard's discovery also notes XAA support.
- After a working sign-in, `/oauth-protected` and `/xaa-protected` serve just the `echo` tool (a simple server, so a successful connection shows something clean); the other tools stay on `/stateless`, `/legacy` and the session-era mock.
- The "asked for OAuth" banner also shows when Auth is already set (a stale token from an earlier wizard run), with wording that says the credentials were rejected (`oauth-prompt.ts`).
- Mocks: `mock-idp.mjs` (:9100) is an OIDC provider (sign-in page: Alex allowed, Bo blocked by policy at the exchange, Cancel), RS256 keys and JWKS, the token-exchange endpoint, client `insomnia-xaa` / `insomnia-xaa-secret`, with break-it flags via `POST /admin/flags` (`denyAll`, `wrongTyp`, `wrongAud`, `expired`, `wrongClient`, `badSignature`, `omitResource`; `POST /admin/reset` clears them). `mock-authorization-server.mjs` (:9000) now advertises the id-jag profile and accepts the jwt-bearer grant, validating the ID-JAG as the draft says (typ, signature via the IdP's JWKS, iss, aud, exp, client_id binding, jti replay) with an `invalid_grant` that names the failed check; its client is `insomnia-xaa` / `insomnia-xaa-as-secret` (deliberately a different secret). ### S5 OAuth calls in the Trace (built 2026-11-20, uncommitted)

- **Decision:** every OAuth call is its own **Call** in the Trace (one correlationId per HTTP exchange, request event then reply event), not one grouped "OAuth" call. A Call is one request and its response, so each probe keeps its own status, duration, headers and body, and a failure points at the exact request. The Stream shows both events of every call.
- What appears (in order of a full run): Unauthenticated request, each metadata candidate tried (a 404 miss is its own red row, then the hit), Client registration (or the CIMD document fetch), **Authorize in browser** (request = the authorize URL we opened; reply = the loopback redirect with `code`/`state`/`iss`, success or error per the checks; `no-response` on timeout, `cancelled` on Cancel), Token exchange, Call the MCP server with the token, and Refresh. Row labels read `<step> · METHOD /path`.
- Tagged with a new protocol-neutral `TraceEvent.flow = 'oauth'`; the Calls row, the Stream row and the detail header all get a small **OAuth** chip with a tooltip. OAuth calls do not offer Edit & replay or Copy cURL (S5d adds replay for steps).
- Mechanism: an `OAuthTrace` callback (`begin(label, request)` returns a handle with `end` / `redirect` / `fail`) threaded through `exchange()`, discovery, flow and token code; `service.oauthTraceFor(requestId)` builds the events with the session sink, so they interleave with MCP calls by sequence. Credential headers are redacted at capture like every other event (the verify call shows `Authorization: <redacted>`); bodies are shown as-is. The expected 401 challenge is a red row (it is an error status).
- Tests: 2 new (`oauth-trace.test.ts`: full run gives 7 calls in order, each request+reply, redirect payload, redaction, cancelled/timeout browser leg).

### S5 auto-refresh on 401 (built 2026-11-20, uncommitted)

- **Rule:** only when the connection's `Authorization` header carries a token **the wizard issued** (`ownsAccessToken`: every token issued for the request is remembered). A header the user typed is never touched. Two triggers, both visible in the trace: (1) **before Connect**, if that token has expired (1 s margin) it is refreshed first; (2) **after a call fails with 401** (`kind: auth`, `status: 401` terminal error), Insomnia refreshes and **retries the call once**, marked as a replay of the failed one (the existing replay mechanism: ↻ badge and "Replay of …"), so the trace reads: call (401, red) -> Refresh the token (OAuth calls) -> the retried call (green). Concurrent 401s share one refresh. No retry for Edit & replay calls that pin exact headers, and none if there is no refresh token or the refresh is rejected (the refresh's own OAuth calls show why).
- **Auth tab stays truthful:** when Insomnia swaps in a new token it bumps `state.oauthRefresh` and the shell writes the new Bearer token into the Auth tab (so what you see is what is sent). A manual **Refresh token** in the wizard also updates the Auth tab; a live connection holding the older token adopts the newer one on its next 401 without another refresh.
- Code: `refreshHeaderToken` and the retry in `run` (`service.ts`), token helpers (`ownsAccessToken`, `currentAccessToken`, `canRefresh`, `isExpired`) in `oauth-token.ts`, the Auth-tab sync in `mcp-debugger-shell.tsx`.
- Tests: 3 integration tests against the real mocks (`oauth-autorefresh.test.ts`): expired token then 401 -> refresh -> retry once -> next call needs no refresh; refresh before Connect; a hand-written token is left alone.
- To click-test: restart the app; mocks running. `curl -X POST localhost:9000/admin/flags -d '{"shortTtl":true}'`, run the wizard on `http://127.0.0.1:8787/oauth-protected` (2 s tokens), Done, Connect, wait a few seconds, set `{"shortTtl":false}`, call a tool: expect a red 401 call, the OAuth refresh calls, then a green retried call; the Auth tab token changes.

## Known shortcuts / not production-ready

- `ProtocolProfile.tabs`/`traceEventKinds`/`builderFields` are the *intended* UI per version, rendered only as a preview in S0 (`profiles.ts`, `mcp-debugger-panel.tsx`).
- `probe.ts` is unauthenticated plain `fetch`: no custom headers, TLS options or HTTP+SSE fallback. Replaced by the ported `MCPHTTPProtocol` in S1.
- The Debugger tab is a scaffold that S1 replaces. The version picker moves into the URL bar.
- `tsc` baseline is already red on this branch (34 errors, grpc/zod) because `node_modules` predates `upstream/develop`; S0 adds none. Run `npm ci` before launching the app.
- S1: sessions and traces are in-memory only (`service.ts`), lost on restart. S2 adds persistence for runs.
- S1: the renderer polls state and trace every 500 ms (`use-mcp-debugger.ts`) instead of subscribing to pushed events.
- S1: direct `fetch` with no TLS options (`sslValidation`), cookies, proxy settings, client certs or user-agent toggle. Insomnia's existing network features are not wired in.
- S1: Auth tab keeps Insomnia's OAuth 2 (`getOAuth2Token`) and drops the legacy MCP auth-flow option; the stepped MCP OAuth debugger is S5.
- S1: params are kept per capability in component state (not stored in `McpPayload`). Resource templates are not listed (Ardi's registry has no template type).
- S1: sessions are not closed on app quit (`closeAllMcpDebuggerSessions` is exported but not wired).
- S1: the old MCP client (`main/network/mcp.ts`, `main/mcp/*`, legacy UI) is still present for stdio requests and unused by HTTP.
- S1: the ported Ardi files in `common/mcp-debugger/protocol/` are intentionally not reformatted to Insomnia's lint rules (about 75 eslint errors, mostly style) so they stay diffable against Ardi. `classify.ts` was edited: the browser-only "cors" guess is replaced by the real network cause.
- Gotcha fixed in S1: `McpRequest.protocolVersion` must be in the model's `optionalKeys` (`insomnia-data/src/models/mcp-request.ts`), otherwise `initModel` prunes it on every save and the version picker silently does nothing. S0 added only the zod field.

## Glossary: "even more auth" (for S8)

- **XAA (Cross App Access)** is enterprise-managed auth. The user signs in once to the company IdP. The client, not the user, gets access to each MCP server, and the admin controls which apps may reach which servers. No per-server consent popup.
- **ID-JAG (Identity Assertion JWT Authorization Grant)** is the token at the center of XAA. The client trades the user's IdP ID token for an ID-JAG aimed at one specific MCP server's auth server (RFC 8693 token exchange).
- **JWT bearer grant (RFC 7523).** The client presents the ID-JAG to the MCP server's auth server and gets back an ordinary access token.
- **EMA (Enterprise-Managed Authorization)** is MCP's official extension that standardizes this flow. XAA is the vendor-neutral name for the same idea. The debugger should show each hop (IdP login, token exchange, JWT bearer) with decoded tokens.
- **CIMD (Client ID Metadata Documents)** is the client_id as an HTTPS URL pointing to a metadata document. It replaces DCR. This sits in S5, not S8.
