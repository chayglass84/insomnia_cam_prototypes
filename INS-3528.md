# INS-3528: Separate Collections from Documents

## Problem

Today, "Generate Collection" on an OpenAPI Document doesn't create a real standalone Collection. It imports the generated `Request`/`RequestGroup` tree directly onto the *same* `scope: 'design'` Workspace that holds the Document's `ApiSpec`. One workspace ends up being both the Document (via its ApiSpec) and a de-facto Collection (via its `/debug` activity's request tree) — duplicated and confusing, and structurally different from a real standalone Collection (`scope: 'collection'` Workspace, fully independent, no ApiSpec).

## What changed

1. **Data model**: `Workspace` gains two optional link fields — `linkedCollectionId` (on a Document workspace, points at its generated Collection) and `linkedDocumentId` (on a Collection workspace, points back at its source Document). Nothing like this existed before.
2. **"Generate Collection" fixed going forward**: it now creates a real, separate `scope: 'collection'` Workspace (same name, same project) instead of importing requests onto the Document's own workspace, and links the two.
3. **Startup migration (forced, not skippable)**: on launch, Insomnia scans git-backed projects for old-format Documents (a design workspace with requests/folders parented directly to it, and no `linkedCollectionId`). If any are found, it shows a short summary dialog ("Found N files using the old collection format — we'll auto-fix this for you and commit the changes") with a single "Fix now" button and no way to defer — clicking it splits each affected Document into a linked Document + Collection pair and removes the old embedded request tree from the Document.
4. **UI links**: the Document header (near the "OpenAPI {version}" text, right-aligned alongside the Generate/Spec format buttons) shows a "View linked collection" button with a collection icon, when a linked Collection exists. The Collection view gained a new equivalent header bar (none existed before), with a right-aligned "View source document" button with a document icon, when a linked Document exists. Both are real buttons (not links) with no arrow/chevron.
5. **Collection sub-tab hidden on Documents**: the Spec/Collection/Tests sub-nav on a Document now only shows Spec and Tests — Collection is no longer nested there.
6. **Old-format check also runs on pull/clone/connect, not just startup**: pulling latest changes into a git-backed project, cloning a new git-backed project, opening an existing local repo folder as a project, and connecting an existing project to a remote all now run the same check immediately after files land on disk — not just at next app launch. **Every one of these always prompts** with the same "Fix now" dialog described above (see `ui/old-format-collection-migration.ts`, the single shared place this prompt lives) — never silent, consistent with startup. For "connect to a repo" specifically: that action itself only stages the connection — the actual clone/import happens the next time the Git Sync panel loads (`loadGitRepository` in `git-service.ts`), so the check is hooked into the Git Sync dropdowns' existing repo-data-load effect (the same pattern the app already uses to detect legacy `.insomnia` folders), not into the "connect" action itself.
7. **Collection file naming fixed to avoid collisions**: the generated collection's git file name is now the Document's name with `_collection` appended (not the same name as the Document's own file), and is checked against every other file already in the project, appending `_2`, `_3`, etc. if still taken.
8. **Migration dialog wording rewritten to be user-facing and feature-first**: leads with what changed and why it helps ("Documents and Collections are now separate...") rather than internal/technical phrasing, before the "Fix now" call to action.

## Why

Kong Insomnia PM request (INS-3528): collections nested inside documents are the wrong/legacy shape; the standalone Collection is correct. Real users will have existing old-format data in git-synced projects that needs migrating in place, with minimal disruption/detail shown to the user.

- `npm run type-check -w packages/insomnia-data` and `-w packages/insomnia`: clean, no errors.
- `eslint` on every touched file: clean, no errors.

## UnitTest/UnitTestSuite handling — resolved via feature flag, not migration

Instead of migrating UnitTest/UnitTestSuite records when a Document is split, the PM's follow-up direction was: treat legacy unit tests as an obsolete feature outright and gate the whole UI behind a setting, defaulted off.

1. **New setting**: `Settings.enableLegacyUnitTests` (boolean, default `false`) — `packages/insomnia-data/common-src/settings.ts`, default in `packages/insomnia-data/src/models/settings.ts`. Exposed in Preferences → General as "Enable legacy unit tests" (`packages/insomnia/src/ui/components/settings/general.tsx`).
2. **Startup auto-enable, sticky-on**: `packages/insomnia/src/ui/legacy-unit-tests-check.ts` (`enableLegacyUnitTestsIfPresent`), wired into `root.tsx`'s startup effects. Counts existing `UnitTestSuite` docs (`database.count`); if any exist and the setting isn't already on, flips it on. Never auto-disables — only a manual Preferences toggle turns it back off, even if the user later deletes all their suites.
3. **Spec/Tests switcher gated**: `document-tab.tsx` returns `null` entirely (no switcher shown, not just the Tests item hidden) when `settings.enableLegacyUnitTests` is false. Since the Tests route is unreachable without this switcher, no separate gate was added on the Tests route itself — only reachable via direct URL nav, which was treated as out of scope.
4. **Warning banner rewritten**: the existing legacy-tests warning banner (`organization.$organizationId.project.$projectId.workspace.$workspaceId.test.test-suite.$testSuiteId.tsx`, near the bottom of the component, ~line 518) previously said tests "will be deprecated... some time in 2026." Replaced with PM-supplied wording: migrate to post-response scripts is best practice, but no plans to remove, 90 days notice if that changes.

## Known shortcuts / not production-ready

- ~~Git commit step is disabled entirely for now~~ **Fixed.** `commitMigratedChangesForProject` (in `generate-linked-collection.ts`) now stages whatever files changed (`window.main.git.gitChangesLoader` → `stageChanges`) and commits them (`commitToGitRepo`) per project, and both the migration flow and the fresh "Generate Collection" action call it. This was required, not just a nicety: on git-backed projects, the Git Sync panel reimports workspace files from disk on basically every page load, and since `linkedCollectionId`/`linkedDocumentId` are new optional fields never written to the tracked YAML, that reimport was silently wiping them from the DB record shortly after they were set — a full-document replace, not a merge (`RepoFileWatcher.importAllFiles` → `upsertDocs` → `database.update`). Committing means the fields round-trip through the tracked file and survive reimport. Trade-off reintroduced: the same test project/repo can no longer be reopened and re-tested repeatedly without git state (commits) changing underneath it — use a fresh test project per run.
- **Startup migration check is a simple root-mounted effect**, not the more robust IPC-gated flow used by `git-repo-migration.ts`/`git-migration.$.tsx`. A production version should probably reuse that mechanism (main-process orchestration, resumable, structured failure reporting) instead.
- **UnitTest/UnitTestSuite handling**: resolved via a feature flag rather than migration (see section above) — no reparenting of test data happens; existing tests stay on the Document workspace exactly where they are, just hidden/shown based on the setting.
- **Migration is scoped to git-backed projects only** (local/cloud projects are not covered), matching the "files"/"commit" framing of the request.
- **Pull/clone/connect hooks are best-effort, not centrally orchestrated.** The check is called from each known renderer call site (both pull dropdowns' success paths and repo-data-load effects, `git.clone.tsx`, and the `cloneGitRepo`/project-creation call sites) rather than from one central place. If a developer adds a new pull/clone/connect entry point later, it won't automatically get this check — a production implementation should centralize this in the main-process git-service functions instead, with the actual prompt/toast triggered from a single renderer listener, not scattered across call sites.
- **Prompts are fire-and-forget, not awaited by their callers.** Since `promptAndFixOldFormatDocumentsInProject`/`promptAndFixOldFormatDocuments` show a modal that waits on the user, none of the call sites `await` them (that would block redirects/toasts on the user dismissing our dialog). This means, in principle, a user could trigger this prompt from two entry points in quick succession (e.g. a pull that also triggers a repo-data reload) and see it queue/reopen. Not addressed here — a production implementation should dedupe/guard against concurrent prompts for the same project.
