# 3593 — Plugins tab for Konnect-linked requests

## Goal

Insomnia's unique advantage is its Kong Konnect integration. Add a **Plugins** tab to the request pane that shows, for a request imported/synced from Konnect, the Kong plugins applied to its route (and inherited from its service/control plane) in execution order. Readonly. Links out to plugin docs and to editing the plugin in Konnect. Includes a "decK command" modal per plugin, and suggests a few common plugins not currently applied.

A **Debugger** tab (Kong debugger / latency breakdown, see [Konnect Debugger docs](https://developer.konghq.com/observability/debugger/)) was also discussed. Plugins is done and pushed; **Debugger is the next part of this same task (3593)** — see "Part 2: Debugger tab" below for the plan to pick up.

## Scope

- New `Tab id="plugins"` / `TabPanel` in `packages/insomnia/src/ui/components/panes/request-pane.tsx`, following the existing Params/Body/Auth/Headers/Scripts/Docs pattern.
- **Visibility:** tab only renders (or shows real content) when the request is Konnect-linked, resolved via the existing chain:
  `Request.konnectRouteKey` → `Workspace.konnectServiceId` (via `Request.parentId` ancestry) → `Project.konnectControlPlaneId` (via `Workspace.parentId`).
  If any link in that chain is missing, show an empty/"not connected to Konnect" state instead of the tab content.
- **Data (real Konnect API, via `packages/insomnia/src/konnect/api.ts`):**
  - New fetcher(s) added to `api.ts` wrapping the Konnect Control Planes Configuration API:
    - `list_plugin_with_route` (RouteId + controlPlaneId) → plugins directly on the route, in order.
    - `list_plugin` (controlPlaneId, optionally filtered) → all plugins in the control plane, used to (a) show service/global-level plugins that also apply, and (b) compute "common plugins not yet applied" suggestions.
    - `fetch_plugin_schema` (pluginName + controlPlaneId) → used for suggestion metadata / config shape shown in the decK modal.
  - Execution order: Kong applies plugin phases in a fixed priority order per plugin type, then route-scoped before service-scoped before global. For this prototype we sort by Kong's documented plugin priority metadata where available, else the order returned by the API — **not a fully authoritative resolution of Kong's real phase-based execution order** (flagged as a shortcut below).
- **Row content per plugin:** name, enabled/disabled state, scope badge (route/service/global), link to `https://developer.konghq.com/plugins/<name>/` docs, link to edit the plugin in the Konnect UI (deep link using controlPlaneId + plugin id), and a "decK command" button.
- **decK command modal:** clicking a plugin's decK button opens a modal with a copyable `deck` CLI snippet representing that plugin's config (e.g. a `deck gateway apply`-style snippet built from the plugin's JSON). This is **illustrative, not a real decK-validated command** (shortcut, flagged below).
- **Suggested plugins:** below the applied-plugins list, show 3–5 common/popular plugins (e.g. rate-limiting, key-auth, cors, request-transformer, prometheus) that are not already applied to this route, each with a docs link and an "Add in Konnect" link. Suggestion list is a static curated list for this prototype, not personalized/algorithmic.

## Known shortcuts / not production-ready

- Plugin execution-order sort is a best-effort approximation, not Kong's real phase-based resolution — flagged inline where implemented.
- decK command modal shows a fabricated illustrative snippet (not real `deck` CLI output/validated command), though the control-plane name it references is real (`Project.name`, kept in sync with `controlPlane.name`).
- Suggested-plugins list is a static hardcoded list, not derived from usage analytics or control-plane context.
- No new persisted schema — reusing existing `konnectRouteKey` / `konnectServiceId` / `konnectControlPlaneId` fields already on `Request`/`Workspace`/`Project`.
- Debugger tab is Part 2 of this task, not yet started — see below.

## Part 2: Debugger tab (not started — pick up here)

**Real REST API confirmed and fully mapped (2026-09-23)** — no MCP dependency needed at runtime, no mocking. Found by driving the actual Konnect UI ("Start debugging" action on a control plane) in Chrome and reading the network tab, then verified end-to-end with a real PAT against Insomnia Airlines (serverless CP) — created a session, sent real `GET /flights` traffic, and pulled back real per-plugin span data matching our test plugins (`pre-function` ~75ms, `key-auth`, `rate-limiting`, `request-validator` all showed up correctly).

**Important nuance surfaced along the way:** there are two unrelated Kong/Konnect debugging mechanisms, easy to conflate:
1. **Header-based single-request debug** (`X-Kong-Request-Debug` / `X-Kong-Request-Debug-Output`, developer.konghq.com/gateway/debug-requests/) — real, documented, but only works when you control the data plane config (hybrid/self-managed, or Dedicated Cloud Gateway via `KONG_REQUEST_DEBUG_TOKEN`). **Does not work on Serverless Cloud Gateways** (confirmed — Insomnia Airlines is `CLUSTER_TYPE_SERVERLESS_V1`). Borrowed this insight from looking at how `rezaloo75/hypersomnia` (a similar prior side-project) implements it, but did not use its code — it explicitly disables this path for serverless CPs.
2. **Session-based Debugger** (below) — the mechanism Konnect actually uses for serverless CPs, since it doesn't require touching data plane config at all. This is what we're building against.

### Real API — `o11y/debug-sessions` (region-based, same `regionalApiBase(region)` pattern as `konnect/api.ts`)

- **Create a session** — `POST /v1/control-planes/{cpId}/o11y/debug-sessions`
  Body: `{ name: string, targets: string[] /* data-plane node IDs, e.g. from GET .../data-plane-nodes */, duration_secs: number (10–1800, UI defaults 60/300), max_samples: number (default 200), capture_traces: true, sampling_rate: number (0–1), sampling_rule: string (empty = all traffic; can scope by route/service) }`.
  Returns the created session object including `target_status` (data-plane compatibility/version check).
- **Poll status** — `GET /v1/control-planes/{cpId}/o11y/debug-sessions/{sessionId}` → has `created_at`/`started_at`/`completed_at`/`timed_out`; treat "in progress" as `completed_at` absent, "done" as present (no separate enum status field observed in the real response — differs from what the MCP tool description implied).
- **List traces (summary)** — `GET .../debug-sessions/{sessionId}/traces?limit=2000` → `{ traces: [{ trace_id, duration_ms, root_service_name, span_sets: [{ matched, spans: [ /* only the root "kong" span, flat */ ] }] }] }`. Good for the top-level "N requests captured, here's total duration each" list — this is the **summary view**.
- **Get one trace (full detail)** — `GET .../debug-sessions/{sessionId}/traces/{traceId}` → real OTel `resource_spans[].scope_spans[].spans[]`, each span has `name` (e.g. `kong.phase.access`, `kong.access.plugin.key-auth`, `kong.tls_handshake`, `kong.read_headers_from_upstream`), `parent_span_id` (builds the phase→plugin nesting), `start_time_unix_nano`/`end_time_unix_nano`, and rich attributes on the root span (route/service/consumer ids, per-phase latency breakdown under `proxy.kong.latency.*`, request/response sizes, TLS info). **This is the real data source for the merged summary+spans view** — walk the parent/child span tree, group by `phase` (derivable from name prefix `kong.phase.<phase>` / `kong.<phase>.plugin.<name>`), and highlight whichever phase/plugin span has outsized `duration` relative to the trace total (mirrors the bottleneck framing from the docs).
- No `stop_session` endpoint found/needed yet — sessions self-complete at `duration_secs`; revisit if we want an explicit early-stop button.

### UI plan (mirror the Plugins tab structure)

- New `Tab id="debugger"` / `TabPanel` in `request-pane.tsx`, same Konnect-linkage gating as Plugins (reuse `resolveKonnectRouteLink`).
- Empty/idle state: a **"Start debugger" button** (this is the key UX difference from Plugins — there's no data to show until the user explicitly starts a capture). Button should be clear that starting a session **captures live upcoming traffic for N seconds**, not historical data — this needs a confirmation/expectation-setting UI since the MCP tool itself requires user confirmation before starting.
- While in progress (`completed_at` absent): show a simple progress/waiting state, polling `GET .../debug-sessions/{sessionId}` on an interval.
- Once done (`completed_at` present): fetch `traces?limit=2000` for the summary list, then `traces/{traceId}` per trace (or lazily on expand) for the full span tree. Render the merged summary+spans view discussed earlier: phase bars sized by aggregate duration, each expandable to show its nested plugin spans, with outsized phases/plugins (relative to trace total) visually flagged as the likely bottleneck.
- Readonly otherwise — no editing capability needed, this is purely diagnostic.

### Test fixtures added to Insomnia Airlines control plane (`0b4545c3-f092-48d3-a2d2-94a666816874`, region `us`)

Added via direct REST calls against the real Control Planes Configuration API (using a user-provided PAT) to get more realistic plugin coverage on `GET /flights` (route `flights-collection`, id `523127aa-215d-4915-ba70-65b75c9fe301`, service `flights-svc`) for testing both the Plugins tab and the upcoming Debugger tab:

- **`key-auth`** — scoped to the `flights-svc` **service** (covers all `/flights*` routes). Consumer `insomnia-tester` created with a key-auth credential.
- **`request-validator`** — scoped to the `flights-collection` **route** only (route-specific, per request). Validates the real optional query params `GET /flights` supports (`origin`, `destination`, `departureDate`, `status` enum, `limit`), all non-required so existing unfiltered calls still pass — only rejects genuinely malformed values (e.g. bad `status` enum → `400`).

- **Caveat:** plain JSON-schema validation on a handful of optional query params is real work but typically sub-millisecond — it may not read as a dramatic bottleneck bar in the Debugger tab's per-phase view the way a slow external call would.
- **`pre-function`** (`FlightsSyntheticLatency`) — added on the `flights-collection` route to guarantee a visible latency bar for the demo: `config.access = ["ngx.sleep(0.075)"]` (75ms, artificial). Tagged `synthetic-latency-demo` — this is a fabricated delay for testing the Debugger tab, not a real plugin's natural cost; remove or note prominently if this control plane is ever used outside of this task's testing.

### Duct tape — read this before extending Part 2

Everything here works against the one control plane we tested (Insomnia Airlines, serverless). Things a future dev (human or AI) should verify, not assume, before this goes further:

1. **The whole `o11y/debug-sessions` API is undocumented.** It's not in Kong's public API catalog. We found it by watching the Konnect UI's network calls, not from a spec. It could change shape without notice. If Konnect ships an official client/SDK for this later, switch to it instead of hand-rolled `fetch`.
2. **`sampling_rule` is always `""` (capture everything on the node), filtered client-side after the fact.** We never confirmed the real filter-expression syntax for scoping a session server-side to one route/service. On a control plane with real production traffic, this session will capture (and Konnect will bill/retain?) traffic from every route on that node, not just the one being debugged. Fine for a lightly-used test CP; potentially not fine elsewhere. Worth confirming the real syntax before this ships broadly.
3. **Session duration is hardcoded to 30s / 200 max samples** (`use-konnect-debugger.ts`). No UI to configure this, unlike the real Konnect "New session" form (which has session name, duration, sampling rate, payload/log capture, CPU profiling — all skipped here).
4. **No persistence across navigation.** Leaving the request and coming back loses the session id and any captured traces — everything lives in component state. The PRD flagged this as an open question before building; it's still open, we just didn't block on it.
5. **Phase grouping uses the raw span parent/child tree, not Kong's named phases** (see the tab component's comment). This is defensible (it's the real data, not a guess) but means the view looks like a flat/nested waterfall rather than the cleanly-labeled "access / tls_handshake / etc" grouping the MCP tool's `get_aggregated_metrics` produces. If that labeled view matters more than correctness-by-construction, get the real name→phase mapping from Konnect's platform team and revisit.
6. **Only tested against a Serverless Cloud Gateway control plane.** Untested: hybrid/self-managed data planes, Dedicated Cloud Gateways, and AI Gateway control planes (which may need `ai_gateway_id` instead of `control_plane_id` — never exercised).
7. **Cancel/DELETE behavior confirmed by testing** (returns `204`, session then 404s on GET — it's actually deleted, not just marked cancelled) but, like everything else here, undocumented.
